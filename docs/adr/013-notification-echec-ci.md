# ADR-013 — Notification d'échec CI : une issue assignée par défaut, un email en couche optionnelle

**Statut** : accepté — revue `adr-challenger` passée, trois objections traitées
**Date** : 2026-09-11
**Semaine du plan** : hors plan — maintenance post-semaine 10 (le plan des 10 semaines est clos, ADR-011/012 acceptés)

## Contexte

La demande est simple en apparence : « une intégration continue avec rapport et email à oussamabelakhdar@gmail.com ». Le rapport existe déjà — `report`/`pages` publient `rapport-html` et `junit` à chaque run (ADR implicite du job `report`, jamais retiré). Ce qui manque est la partie email, et c'est elle qui pose une vraie question d'architecture, pas une question d'outil.

**Fait vérifié avant toute décision** : `gh secret list -R OussamaBelakhdar/rwa-quality-platform` ne renvoie **aucun secret**. Ce n'est pas un oubli — c'est le résultat cumulé de trois ADR qui ont chacun refusé d'en ajouter un pour la même raison, P6 (« reproductible par un inconnu, sans compte tiers, sans secret ») :

| ADR     | Ce qu'il a refusé                                                                                                                                                            |
| ------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ADR-003 | Cypress Cloud — `record`, `CYPRESS_RECORD_KEY`                                                                                                                               |
| ADR-010 | Un tenant Auth0 réel comme **seule** option — gardé en option locale par défaut, le tenant réel restant un choix d'opérateur sur son poste, jamais câblé dans la CI partagée |
| ADR-011 | `cy.prompt` en CI — compte Cypress Cloud, résultat non déterministe dans un gate bloquant                                                                                    |

Un email SMTP personnalisé exige un couple d'identifiants (adresse + mot de passe d'application). Ce serait donc le **premier secret jamais commis à la configuration CI** de ce dépôt. La question n'est pas « peut-on envoyer un email », c'est « à quel prix pour P6 », et la réponse doit être écrite comme les trois précédentes.

**Deuxième fait vérifié, indépendant de la demande mais découvert en creusant le pipeline existant** : le job `firefox` de `.github/workflows/e2e.yml` ouvre déjà une issue sur échec — `gh issue create --title "Firefox rouge — ..." --label ci ...`. `gh label list` sur le dépôt ne renvoie **aucun label nommé `ci`** (12 labels : bug, accessibility, documentation, duplicate, enhancement, good first issue, help wanted, invalid, question, wontfix, dependencies, javascript). `gh issue create --label` échoue si le label n'existe pas. Ce code n'a simplement jamais été exercé en échec : le seul run Firefox réel documenté est vert. C'est exactement la classe de défaut qu'ADR-012 a été écrit pour éliminer — une garde jamais prouvée en est une qui ment par omission — et cet ADR ne peut pas proposer un mécanisme de notification par issue sans d'abord corriger celui qui existe déjà et qui casserait au premier rouge.

## Options considérées

| Option                                                                                | Avantages                                                                                                                                                                                                                                                                                                                                                                                                             | Inconvénients                                                                                                                                                                                                                                                                                                                                          | Coût                                                                                                                                                                                                                                |
| ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A — Notification GitHub native seule** (issue + assignation sur échec, zéro secret) | P6 intact pour tout inconnu qui clone ; réutilise et corrige le mécanisme déjà présent (`firefox`) ; l'assignation déclenche l'email par le mécanisme propre de GitHub, sans rien commettre                                                                                                                                                                                                                           | Contenu de l'email non personnalisable — c'est GitHub qui l'écrit, pas nous ; dépend des préférences de notification du compte assigné                                                                                                                                                                                                                 | ~20 lignes + création d'un label                                                                                                                                                                                                    |
| **B — Email SMTP personnalisé seul** (Gmail, `dawidd6/action-send-mail`)              | Contrôle total du contenu (résumé des 4 jobs, lien du rapport, mise en forme)                                                                                                                                                                                                                                                                                                                                         | **Premier secret du dépôt** ; casse P6 pour ce job précis ; un fork ou un inconnu qui clone n'a par définition jamais ces secrets, donc le mécanisme serait silencieusement inactif pour tout le monde sauf le propriétaire — sans qu'un lecteur ne le sache en lisant le YAML seul                                                                    | ~30 lignes + 2 secrets + une dépendance externe (action tierce)                                                                                                                                                                     |
| **C — Les deux, en couches** _(retenue)_                                              | A reste le comportement PAR DÉFAUT, prouvable par quiconque clone (P6 intact) ; B s'active UNIQUEMENT si les deux secrets existent (`secrets.SMTP_USERNAME != ''`) — invisible et inoffensif pour un inconnu, utile pour le propriétaire s'il choisit de le configurer. Même architecture qu'ADR-010 : un chemin local qui marche toujours, un chemin réel qui s'active par configuration explicite, jamais l'inverse | Deux mécanismes à maintenir plutôt qu'un ; la condition `secrets.X != ''` doit être lue pour comprendre que B est optionnel — sans ce commentaire, un lecteur pourrait croire le dépôt dépendant d'un compte Gmail                                                                                                                                     | **118 lignes, mesuré** (`git diff --stat`) — l'estimation initiale de ~45 était fausse d'un facteur 2,6 ; elle ne comptait ni les commentaires expliquant chaque garde, ni la garde fork/PR ajoutée après la revue `adr-challenger` |
| **D — Se contenter des notifications GitHub par défaut, sans rien coder**             | Coût nul                                                                                                                                                                                                                                                                                                                                                                                                              | N'envoie rien de propre à ce dépôt sur un `push` de branche (seulement sur PR par défaut selon les réglages du compte) ; aucune trace dans le dépôt de ce qui se passe si la CI est rouge — reproductibilité de l'_information_, pas seulement de la _suite_, cassée pour un futur relecteur qui n'a pas accès aux réglages de notification d'un tiers | 0                                                                                                                                                                                                                                   |

L'option qu'un recruteur suggérerait spontanément est **B** — « ajoute juste une clé API et envoie l'email ». Elle perd ici pour la même raison que Cypress Cloud a perdu en semaine 6 et `cy.prompt` en semaine 10 : elle rendrait un mécanisme de CI **invisible à l'audit** pour quiconque n'a pas les secrets du propriétaire, dans un dépôt dont la promesse P6 est justement l'inverse.

## Décision

**Option C.** Un nouveau job `notifier` dans `.github/workflows/e2e.yml`, `needs: [qualite, e2e, component, auth0]` — les **4 jobs bloquants seulement**, pas `quarantine`/`playwright`/`firefox`, qui sont déjà non bloquants et gèrent leur propre signal. `if: always()`.

1. **Correctif préalable** : créer le label `ci` sur le dépôt (`gh label create ci`, une fois, hors CI — ce n'est pas un secret, c'est de la configuration de dépôt). Sans lui, le job `firefox` échouerait à la première Firefox rouge, et `notifier` échouerait avec lui.
2. **Échec → issue** : si `contains(needs.*.result, 'failure')`, chercher une issue ouverte labellée `ci` (`gh issue list --label ci --state open`). Si elle existe, la commenter (lien du run, résultat des 4 jobs) ; sinon en créer une, assignée à `OussamaBelakhdar`. C'est l'**assignation**, pas un secret, qui déclenche la notification par email de GitHub — le mécanisme est celui déjà éprouvé par `firefox`, étendu aux jobs qui comptent vraiment (bloquants) et corrigé du label manquant.
3. **Retour au vert → fermeture** : si tout est vert et qu'une issue `ci` reste ouverte, la commenter puis la fermer. Même principe que la quarantaine du projet (`.claude/rules/testing.md` #10 et le job `quarantine`) : un signal qui ne se referme jamais est un signal qu'on apprend à ignorer.
4. **Email personnalisé, en couche optionnelle** : une étape `if: contains(needs.*.result, 'failure') && secrets.SMTP_USERNAME != ''`, `uses: dawidd6/action-send-mail@03a02a49409134de07636216fb379a026c52991e # v21`, destinataire `oussamabelakhdar@gmail.com`, sujet et corps incluant le lien du run et le détail des 4 jobs requis. Le SHA est résolu depuis `gh api repos/dawidd6/action-send-mail/tags` — action tierce vérifiée et épinglée par SHA complet, comme toutes les autres du pipeline (ADR implicite du `e2e.yml` existant : jamais de tag mutable).

Sans les secrets `SMTP_USERNAME`/`SMTP_PASSWORD`, l'étape 4 ne s'exécute jamais et n'apparaît dans aucun log — c'est la condition, pas une variable d'environnement absente qui échouerait bruyamment, qui la neutralise. Un inconnu qui clone le dépôt obtient les étapes 1 à 3 sans rien configurer ; le propriétaire obtient l'email en plus s'il le choisit.

## Revue `adr-challenger`

Trois objections, toutes traitées avant d'accepter — la troisième par du code, pas seulement par du texte.

1. **Collision de label.** Le job `notifier` cherchait/fermait une issue via `--label ci` — **le même label que `firefox`** utilise déjà pour ses propres rouges hebdomadaires. Vérifié en relisant les deux jobs côte à côte : `notifier` aurait pu commenter/fermer une issue ouverte par `firefox` (et inversement, `firefox` n'ayant aucune recherche, en aurait ouvert une seconde à côté d'une déjà ouverte par `notifier`). L'invariant annoncé plus haut (« l'issue `ci` ouverte = rouge non traité ») n'était donc pas garanti — deux flux différents écrivant dans le même compartiment sans jamais se corriger. **Corrigé** : `notifier` utilise désormais son propre label, `ci-bloquant`, créé séparément (`gh label create`). `firefox` garde `ci`, inchangé.
2. **L'étape email n'a jamais tourné.** Vrai, et resté implicite dans la première rédaction — qui affirmait pourtant en Conséquences que l'email « porte exactement le contenu voulu » comme un fait acquis. Aucun secret `SMTP_*` n'existe sur ce dépôt au moment d'écrire ceci ; seules la syntaxe YAML et la forme des entrées de `dawidd6/action-send-mail` sont vérifiées, pas l'envoi réel. **Corrigé** : le commentaire du job et cette section le disent maintenant explicitement, plutôt que de l'affirmer comme acquis.
3. **PR venant d'un fork externe.** Le job tournait sur `pull_request` sans distinguer une PR de fork — où GitHub force `GITHUB_TOKEN` en lecture seule quel que soit le bloc `permissions:` déclaré, et où `--assignee OussamaBelakhdar` échoue si ce compte n'est pas collaborateur du fork. La promesse P6 du Contexte (« reproductible par un inconnu ») était donc fausse dans exactement le cas qu'un relecteur testerait en premier. **Corrigé par deux mécanismes complémentaires**, pas un seul : `continue-on-error: true` au niveau du job (un échec de `notifier` ne colore jamais rouge le CI d'un contributeur pour une raison qui n'est pas la sienne — même garde que `firefox`/`quarantine`/`playwright`), et une variable `est_meme_depot` qui neutralise les étapes d'écriture d'issue quand `github.event.pull_request.head.repo.full_name != github.repository`.

## Conséquences

- **Positives** :
  - Le mécanisme de notification par défaut est **prouvable par quiconque pousse sur son propre dépôt** — cloner, faire échouer un job bloquant, observer l'issue `ci-bloquant` et son assignation, aucun compte tiers requis. Pour une PR de fork externe, il ne s'exécute simplement pas (garde `est_meme_depot`) plutôt que d'échouer bruyamment.
  - Corrige deux défauts latents réels découverts en construisant cette décision, pas après coup : `firefox` sans label `ci` (jamais exercé, seul run réel vert), et la collision de label trouvée par `adr-challenger` avant tout commit.
  - L'email personnalisé, **une fois exercé avec de vrais secrets** (non fait à ce jour), est censé porter le résumé des 4 jobs et un lien direct — ce qu'une notification GitHub générique ne fait pas. Cette phrase reste une intention vérifiée sur la forme, pas sur le fond, tant qu'aucun run réel ne l'a confirmée.
- **Négatives assumées** :
  - **P6 est rompu pour l'étape email, explicitement et seulement pour elle** — même exception qu'ADR-010 assume déjà pour un tenant Auth0 réel : un chemin optionnel, jamais celui que suit un inconnu par défaut.
  - Deux secrets à créer et faire vivre côté GitHub (`SMTP_USERNAME`, `SMTP_PASSWORD` — un mot de passe d'application Gmail, pas le mot de passe du compte) : hors du dépôt, donc hors de portée de cet ADR pour leur rotation.
  - Une dépendance à une action tierce (`dawidd6/action-send-mail`) pour l'étape email seulement — les étapes d'issue n'utilisent que `gh`, déjà présent sur tout runner GitHub.
  - L'issue de suivi peut recevoir plusieurs commentaires rapprochés si plusieurs jobs bloquants échouent sur des commits successifs avant qu'un correctif ne passe — assumé, c'est le comportement voulu (un seul signal actif, pas un par run).
  - **L'étape email reste non exercée avec de vrais secrets** (négatif ouvert, pas fermé par cet ADR) : la première fois qu'elle tournera pour de vrai sera la vérification empirique, comme ADR-011 l'a fait pour `cy.prompt`.
- **Surveillé via** : la présence de l'issue `ci-bloquant` elle-même (ouverte = rouge non traité) ; aucun script de gate dédié — ce n'est pas un invariant du code du dépôt, c'est un comportement de son CI.

## Réversibilité

Retirer le job `notifier` de `.github/workflows/e2e.yml`. **Aucune couche L0-L5 n'est touchée** : ni la suite, ni les commandes, ni les gates n'en dépendent — exactement la garantie que la borne 1 d'ADR-011 donnait pour `cypress/manual/`, ici pour un job de notification.

Si les secrets `SMTP_USERNAME`/`SMTP_PASSWORD` n'ont jamais été créés, il n'y a rien à retirer côté dépôt pour annuler l'étape email : elle n'a simplement jamais tourné. Les labels `ci` et `ci-bloquant` peuvent rester sans coût — un label inutilisé n'est pas une dette, contrairement à une gate inutilisée.
